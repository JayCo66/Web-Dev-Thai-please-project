# จุดแก้ชื่อ รางวัล ภาพ และการรวม Git

## ชื่อรางวัลมาจากไหน

ชื่อกับราคารางวัลลุ้นอยู่ที่ **backend/src/services/rewardCatalog.js** แก้ name และ referenceValue ในรายการที่ต้องการได้จากไฟล์เดียว เก็บ key, legacyNames และ legacyImages ไว้เพื่อให้ระบบรู้จักรายการเดิม

catalogService.js อ่านรายการนี้ไปอัปเดตตาราง rewards ส่วน rewardController.js อ่าน rewards.name แล้วส่ง API ให้ ThaiPlus.jsx แสดงผ่าน prize.name

เมื่อแก้ชื่อใน source ให้รัน npm run db:upgrade ใน backend ของ branch ปัจจุบันเพื่อ sync ค่าเข้าฐานข้อมูลเดิม สคริปต์จะข้าม DDL ที่เคยทำแล้ว และอัปเดต catalog ต่อ ไม่ใช่การล้างฐานข้อมูล

## ทำไมรถซ้ำและราคาเป็นศูนย์

สาเหตุเดิม: สคริปต์ค้นหาแถวเก่าด้วยชื่อเต็ม เมื่อเปลี่ยนชื่อแล้วหาไม่พบจึง INSERT เป็นแถวใหม่ DB จึงมีรถชื่อยาว reward_id=7 และชื่อสั้น reward_id=9 พร้อมกัน หน้าเว็บแสดงทั้งสองเพราะทั้งคู่ is_active=true ไม่ใช่ React วาดซ้ำ

ราคาศูนย์เป็นอีกปัญหาหนึ่ง: backend เคย lookup ราคาด้วยชื่อสั้นเท่านั้น ชื่อยาวจึงไม่มีราคา และ frontend ใช้ Number(value || 0) กลายเป็น 0.00

แก้แล้ว: จับคู่รายการด้วยชื่อเดิมและเส้นทางภาพที่กำหนด เก็บแถวเก่าสุดเป็นรายการหลัก ปิด is_active ของรายการซ้ำ ไม่ลบแถวหรือสิทธิ์เก่า รวมชื่อและราคาไว้ rewardCatalog.js และไม่แสดง 0.00 แทนราคาที่ไม่รู้ (แสดงยังไม่ระบุราคา)

## กรอกจำนวนสิทธิ์

maxTickets = min(100, floor(tokens / tokenCost)) หน้า ThaiPlus ลดค่าที่กรอกเกินลงทันที มี 60 แต้ม ราคา 25 กรอก 100 จะเหลือ 2 สิทธิ์ ใช้ 50 เหลือ 10 ไม่แสดงยอดติดลบ Backend ยังตรวจแต้มจริงและล็อกธุรกรรมเองเพื่อรับมือการเปิดหลายแท็บ

## ภาพมูลนิธิ

backend/src/services/charityMedia.js เป็นจุดจับคู่ชื่อใน DB กับไฟล์ใน frontend/public/assets/charities API ส่ง coverImageUrl, logoImageUrl, imageKind และ imageCaption

ทั้ง 28 รายการใช้ภาพเฉพาะองค์กร: มีภาพกิจกรรม 10 แห่ง, โลโก้เป็นภาพหลัก 17 แห่ง และโปสเตอร์มูลนิธิเด็กโรคหัวใจ 1 แห่ง ภาพโลโก้ Google บางไฟล์เป็น thumbnail ขนาดเล็กจึงจำกัดการขยายและใช้ object-fit:contain ไม่ตัดตรา ดู docs/charity-media-v6.json สำหรับลิงก์ต้นฉบับ สายใจไทยโหลดได้จาก URL เดิมเติม query parameter หลัง URL หลักตอบ 403

## Schema และ migration คืออะไร

**Schema คือแบบของตาราง** เช่น reward_redemptions มีคอลัมน์อะไรบ้างและชนิดข้อมูลอะไร เหมือนหัวคอลัมน์ใน Excel

**ข้อมูลคือแถวที่อยู่ในตาราง** เช่น ผู้ใช้คนใดแลกตั๋วอะไรไปแล้ว ไม่ใช่ตัว schema

**Migration คือชุดคำสั่งเปลี่ยนโครงสร้างหรือแปลงข้อมูลเดิมให้เป็นแบบใหม่** ตัวอย่างเพิ่มคอลัมน์หมายเลขบาร์โค้ด โดยไม่ลบประวัติเก่า:

```sql
-- ตัวอย่างเพื่ออธิบาย ไม่ใช่ migration สำหรับรวมสอง branch ที่เสร็จแล้ว
ALTER TABLE reward_redemptions ADD COLUMN barcode_number VARCHAR(100) NULL;
```

ในงานนี้ ทั้งสอง branch ตั้งชื่อตารางว่า reward_redemptions เหมือนกัน แต่ในเครื่องใช้ kind/code/metadata ส่วน main ใช้ reward_type/voucher_code/ticket_number นั่นคือคนละแบบตาราง ไม่ได้หมายความว่ามีสองตารางชื่อเดียวกันอยู่ใน DB เดียว

ถ้านำ backend ของ main มาทับ มันจะอ่าน voucher_code แต่ DB เดิมมี code จึงอาจ error ว่าไม่มีคอลัมน์ ต้องเลือกว่าจะเก็บแบบใดหรือเพิ่มคอลัมน์ใด แล้วเขียนคำสั่งเพิ่ม/แปลงค่าโดยรักษาสิทธิ์และประวัติเดิม เช่น code ของคูปองอาจย้ายไป voucher_code และ code ของสิทธิ์ลุ้นอาจย้ายไป ticket_number ต้องแยกตาม kind ไม่ใช่เปลี่ยนชื่อ code ทิ้งทั้งคอลัมน์

**สำเนาฐานข้อมูล** คือ copy DB เดิมไปอีกชื่อหนึ่งเพื่อทดลองแปลงก่อน แล้วตรวจว่าจำนวนตั๋ว ประวัติ และยอดโทเค็นยังถูกต้อง ก่อนใช้ชุดคำสั่งที่ตรวจแล้วกับฐานหลัก

รายการรถซ้ำในภาพกับ schema สอง branch เป็นคนละปัญหา การแก้รถซ้ำรอบนี้อัปเดตข้อมูลรางวัลเท่านั้น ไม่ต้องเพิ่มคอลัมน์ ไม่ต้อง reset/import SQL ใหม่ และยังไม่ได้รวม main

## Git กับ database เป็นคนละเรื่อง

ไม่ต้องล้าง DB หรือ import seed ใหม่เพื่อแก้ merge conflict และไม่อาจรับประกันว่า branch ที่แก้ไฟล์เดียวกันจะไม่มี conflict

1. ตรวจ git status และบันทึกงานปัจจุบันให้ครบก่อนรวม ระวังอย่า stage .env หรือข้อมูลส่วนตัว
2. แยก integration branch จาก improveUxUi เพื่อให้งานปัจจุบันยังอยู่ ตัวอย่างหลัง commit งานแล้ว:

```powershell
git switch -c integration/main-20261030
git fetch origin
git merge --no-commit --no-ff origin/main
```

3. แก้ conflict ทีละส่วน ไม่เลือก ours/theirs ทั้งไฟล์ schema/controller เพราะระบบสอง branch ใช้สัญญา API และ schema ต่างกัน ถ้ายังไม่พร้อมรวม ใช้ git merge --abort กลับไปก่อนเริ่ม merge ได้เมื่อเริ่มจากสถานะสะอาด
4. ตกลงโครงสร้างกลางก่อน: reward_redemptions ของงานในเครื่องใช้ kind/code/metadata/request_key ส่วน main ใช้ reward_name/voucher_code/ticket_number จึงต้องเขียน migration แปลงข้อมูลให้เข้ากัน เก็บ request_key/event_key และ unique indexes ที่ป้องกันแจก/หักซ้ำไว้
5. สำรอง DB เดิมก่อน แล้วทดลอง migration บนสำเนาฐานข้อมูล ไม่ใช้ reset, db push --accept-data-loss หรือ import thai_please_schema.sql ทับข้อมูลผู้ใช้
6. เมื่อ schema กับ code ตรงกัน จึง generate Prisma client, รัน tests และ functional checks ก่อนรวม integration branch กลับหรือเปิด PR

ขั้นตอนนี้เป็นแนวทางให้ทำต่อ ยังไม่ได้ merge/commit/push ในรอบนี้ และไม่มีการเปลี่ยน schema ฐานข้อมูลจากการเพิ่มภาพหรือจำกัดจำนวนสิทธิ์

## ความครอบคลุมหมวด

ข้อมูลโครงงานมี 28 แห่ง แบ่งหมวดการศึกษา/เยาวชน สิ่งแวดล้อม ชุมชน และสุขภาพ หมวดละ 7 ครบตาม 4 หมวดที่ schema รองรับ ไม่ใช่ทะเบียนมูลนิธิทั้งหมดของไทย องค์กรสำหรับผู้สูงอายุ สตรี/ความรุนแรงในครอบครัว และสุขภาพจิตโดยตรงยังไม่เด่น หากขยายควรเพิ่มองค์กรที่ตรวจสอบแล้วภายใต้หมวดเดิมหรือใช้ tag แทนการเพิ่ม enum หมวดทันที (ต้องปรับทั้ง DB/API/UI ถ้าเพิ่ม enum)
